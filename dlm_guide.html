1. Executive Summary & Problem Statement

1.1 Why Does This Project Exist?

In a traditional single-machine program, coordinating access to shared data is straightforward: operating systems provide lightweight primitives such as std::mutex, std::shared_mutex, and std::condition_variable. However, in modern cloud-scale distributed databases—such as Google Spanner, CockroachDB, and TiDB—data is partitioned across dozens or hundreds of independent computers connected by a network.

When two users on different physical nodes attempt to modify the same account balance simultaneously, OS mutexes cannot communicate across network cables. If uncoordinated:

  • Dirty Reads occur: Transaction B reads uncommitted modifications made by Transaction A.
  • Lost Updates occur: Transaction B overwrites Transaction A's modifications without knowing they occurred.
  • Distributed Deadlocks occur: Node 1 waits for Node 2, while Node 2 waits for Node 1, freezing the entire cluster indefinitely.
Project Objective: We built a production-grade Distributed Lock Manager (DLM) from scratch in modern C++17 that implements Strict Two-Phase Locking (SS2PL) over TCP sockets, provides Local and Global Deadlock Detection using directed Wait-For Graph (WFG) cycle detection, guarantees distributed atomicity via Two-Phase Commit (2PC), logs mutations to disk via Write-Ahead Logging (WAL), and provides a real-time Interactive Visual Dashboard (UI).

2.2 Data Structures Inside `LockManager`

The core locking engine (include/dlm/lock_manager/LockManager.h) manages local resources through thread-safe indexes: 

class LockManager {
private:
    mutable std::mutex mutex_;
    std::condition_variable cv_;

    // ResourceId -> Current Lock Status (Mode + Set of Owners)
    std::unordered_map<ResourceId, LockEntry> lockTable_;

    // ResourceId -> Queue of waiting transactions: [(TxnId, Mode)]
    std::unordered_map<ResourceId, std::vector<std::pair<TxnId, LockMode>>> waiters_;

    // TxnId -> Set of resources held by this transaction (for bulk commit release)
    std::unordered_map<TxnId, std::unordered_set<ResourceId>> txnLocks_;
};

3. Deep Dive: Core Algorithms & Code Walkthrough

3.1 Strict Two-Phase Locking (SS2PL) & Lock Compatibility

To ensure serializability, our Lock Manager uses two modes with a strict compatibility matrix:

Requested Mode \ Held Mode Resource is FREE Held in SHARED Held in EXCLUSIVE
SHARED (Read Lock) ✅ GRANTED ✅ GRANTED (Coexists) ❌ BLOCKED (Must Wait)
EXCLUSIVE (Write Lock) ✅ GRANTED ❌ BLOCKED (Must Wait) ❌ BLOCKED (Must Wait)

Code Walkthrough: `acquireLock()` with Timeout

When a transaction requests a lock: 

bool LockManager::acquireLock(TxnId txnId, const ResourceId& resId, LockMode mode,
                              std::chrono::milliseconds timeout) {
    std::unique_lock<std::mutex> lock(mutex_);

    // Step 1: Enqueue in wait list
    waiters_[resId].push_back({txnId, mode});

    // Step 2: Compatibility predicate lambda
    auto canAcquire = [&]() {
        // If aborted while waiting, wake up immediately!
        if (!isStillInWaitQueue(txnId, resId)) return true;

        if (lockTable_.count(resId)) {
            if (!isCompatible(lockTable_[resId], txnId, mode)) return false;
        }

        // FIFO queue ordering: check if anyone ahead of us wants EXCLUSIVE
        for (const auto& [wTxn, wMode] : waiters_[resId]) {
            if (wTxn == txnId) break; // Reached ourselves
            if (mode == LockMode::EXCLUSIVE || wMode == LockMode::EXCLUSIVE) return false;
        }
        return true;
    };

    // Step 3: Sleep on Condition Variable
    bool ok = cv_.wait_for(lock, timeout, canAcquire);

    // Step 4: Cleanup wait queue & grant lock if acquired
    ...
}
Key Concurrency Mechanism: When cv_.wait_for(lock, timeout, canAcquire) is called, std::unique_lock atomically releases the underlying mutex while putting the thread to sleep. This allows other transactions to execute operations concurrently. When cv_.notify_all() is invoked upon lock release, blocked threads re-acquire the mutex and re-evaluate their acquisition conditions.

3.2 Wait-For Graph (WFG) Construction

A Wait-For Graph is a directed graph $G = (V, E)$ where nodes are transactions and edges represent waiting dependencies. `LockManager::getWaitForEdges()` constructs directed edges $(T_{\text{waiter}} \to T_{\text{holder}})$ directly from internal wait queues: 

std::vector<WaitEdge> LockManager::getWaitForEdges() const {
    std::lock_guard<std::mutex> lock(mutex_);
    std::vector<WaitEdge> edges;

    for (const auto& [resId, waitQueue] : waiters_) {
        const auto& entry = lockTable_.at(resId);
        for (const auto& [waiterTxn, mode] : waitQueue) {
            for (TxnId holderTxn : entry.owners) {
                if (waiterTxn != holderTxn) {
                    edges.push_back({waiterTxn, holderTxn, resId});
                }
            }
        }
    }
    return edges;
}

4. Deadlock Detection & Two-Phase Commit

4.1 Tarjan 3-Coloring DFS Cycle Detection

A deadlock exists if and only if the Wait-For Graph contains a directed cycle. Our DeadlockDetector uses a 3-coloring Depth-First Search algorithm:

  • WHITE (0): Node has not yet been visited.
  • GRAY (1): Node is currently on the active DFS recursion stack.
  • BLACK (2): Node and all of its descendants have been fully explored.
[T1] ──holds R1, wants R2──► [T2] ▲ │ │ holds R2, wants R1 └─────────────────────────────┘ (Cycle detected when DFS reaches a node marked GRAY!)

Youngest Victim Selection Policy

Once a cycle is detected (e.g. $T_1 \to T_2 \to T_1$), exactly one transaction must be aborted to break the cycle. Our policy selects the youngest transaction (highest `TxnId`): 

TxnId DeadlockDetector::selectVictim(const std::vector<TxnId>& cycle) {
    return *std::max_element(cycle.begin(), cycle.end());
}
Why Pick the Youngest Transaction?
  1. Minimizes Wasted Work: Older transactions have acquired more locks and performed more computation; aborting the youngest minimizes rollbacks.
  2. Prevents Starvation: Because transaction IDs monotonically increase, an older transaction's ID stays constant. It is guaranteed to eventually become the oldest in any conflict and will never be starved.

4.2 Two-Phase Commit (2PC) Consensus Protocol

When a transaction touches resources on multiple nodes, atomic commitment requires the 2PC protocol implemented in TwoPCCoordinator.cpp:

COORDINATOR (Node 1) PARTICIPANTS (Node 2 & Node 3) │ │ │ ───────────── Phase 1: PREPARE ───────────► │ (Check locks & WAL log) │ ◄────────── VOTE_YES / VOTE_NO ──────────── │ │ │ [Evaluate Votes] │ All YES? ──► COMMIT │ Any NO? ──► ABORT │ │ │ │ ───────── Phase 2: COMMIT / ABORT ────────► │ (Evict locks & flush WAL) ▼ ▼
  1. Phase 1 (Prepare): Coordinator sends PREPARE message to all participant nodes. Each participant writes PREPARE to its local WAL log and votes VOTE_YES or VOTE_NO.
  2. Phase 2 (Decision): If all votes are VOTE_YES, coordinator logs COMMIT and broadcasts GLOBAL_COMMIT. If any node votes VOTE_NO or times out, coordinator broadcasts GLOBAL_ABORT.
